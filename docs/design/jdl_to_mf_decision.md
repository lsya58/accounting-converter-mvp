# JDL→Money Forward の判断記録

日付: 2026-10-31 / 判断: **NO-GO（製品機能としても技術スパイクとしても今は作らない）**

## 前提として確認した事実（repo内）

| 事実 | 根拠 |
|---|---|
| 出力側は `OutputAdapter` 抽象があるが、実装は JDL だけ。MF への serializer は存在しない | `adapters/output/` |
| JDL の読込（`JdlMigrationParser`）は JDL→JDL 1,158件の実Importで使用済み。行・税literal・部門・摘要を取り出せる | `adapters/input/jdl/observed_parser.py` |
| 複合仕訳の「物理行と行ごとの摘要」は共通モデルにない。MF入力は `moneyforward_*`、JDL入力は `physical_rows` と、入力元ごとに別キー | 各 parser |
| JDL 出力の preflight は MF 専用の `moneyforward_verified_description_rows` と MF入力前提の条件（6か所）を使う。弥生入力の複合仕訳（1D3C以外）は「行単位摘要を保持できない」で BLOCK される | `adapters/output/jdl/preflight.py`、`application/first_release_workflow.py` |
| 税の実機Evidence（capability composition）は MF の税区分名で索引されている。JDL側の挙動は入力元に依存しないのに、弥生からは再利用できない | `application/moneyforward_tax_excluded_evidence.py` |
| 手元の MF 仕訳帳CSV（19列）に税額列はない。実データ482件の税額はすべて空 | `profiles/known_formats.py`、実データ |

## 外部情報（ユーザー提供、repo内Evidenceなし）

- MF には公式の「他社ソフトデータの移行 > JDL（IBEX出納帳）」があり、科目・補助・部門・税区分・インボイスを MF 側でマッチングできる
- MF の仕訳帳インポートでは、借方税額・貸方税額に 0 または空欄しか入れられない

公式の JDL 取込が、マッチング結果を会社単位で保存して次回以降に再利用するかは **不明**。

## Route A（MF公式 JDL取込）と Route B（自前変換 → MF通常インポート）

| 観点 | Route A | Route B |
|---|---|---|
| 開発コスト | 0 | MF serializer・`MfTargetContext`・MF側検証・MF実機Evidenceが新規 |
| 利用者の操作 | MF画面でマッチング | 本アプリで初回マッピング → MFで取込 |
| マッピングの保存 | 不明 | 会社設定に保存できる |
| 税区分 | MF側でマッチング | 事前に確定できる |
| 明示した税額・端数 | MFが再計算するとみられる | 税額を入れられない（上記が事実なら）。JDLの明示税額は保持できない |
| インボイス・取引先・タグ・メモ | JDLに元々ない | 同じ。JDLから復元できない |
| 行ごとの摘要・複合仕訳 | 不明 | 取引Noで表現可能 |
| 会計期間の分割 | 不明 | 既存ツールで可能 |
| 厳密な往復検証 | 不可 | MF再Exportに税額列がないため、税額は比較できない |

## JDL→MF で失われる・持てない情報

| 項目 | JDL元データ | MFインポートで持てるか | JDLから復元できるか |
|---|---|---|---|
| 科目・補助 | コード+名称 | 名称のみ | 名称の対応付けが必要（コードは失われる） |
| 課区・税区・税入力方法 | あり | MF税区分名 | 対応付けで可能 |
| 明示税額・端数 | あり | 0か空欄のみ | **不可**（MFの再計算に依存） |
| 部門 | コード+名称 | 名称 | 名称で可能 |
| 行ごとの摘要 | あり | あり | 可能 |
| 取引先 | なし（本アプリは摘要へ追記） | あり | 原則不可（摘要の追記文字列を逆解析するのは規約依存） |
| インボイス・タグ・メモ | なし | あり | 不可 |

MF→JDL→MF は、取引先・インボイス・タグ・メモが JDL に残らないため可逆ではない。「MF⇄JDL 双方向対応」という表現は誤解を招くので使わない。

## NO-GO の理由

1. **顧客の困りごとがない**: 父親事務所の流れは「顧問先がMF → 事務所がJDL」。JDL→MF の需要は確認されていない。
2. **公式機能と重なる**: 単発の移行なら公式の JDL 取込で足りる。差別化になりうる「マッピングの保存」は、公式の挙動が不明なまま主張できない。
3. **本アプリの強みが出せない**: 強みは「実機での厳密な往復検証・欠落ゼロ」。MF側は税額を入れられず、再Exportにも税額列がないため、その強みを MF target では証明できない。
4. **弥生対応に効かない**: JDL→MF で作るのは MF の serializer。弥生→JDL に必要なのは JDL 出力の入力元非依存化で、別物。

## 次に作るもの（弥生実機待ちの間）

> 2026-10-31 実施済み: [入力元に依存しない JDL target](mf_tax_capability_composition.md#入力元に依存しない-jdl-target2026-10-31)。

**JDL 出力を入力元に依存させない**（大規模refactorではない）:

- 物理行と行ごとの摘要を共通モデル（domain）の概念にし、MF・JDL・弥生の各 parser がそこへ詰める。JDL preflight は MF専用関数ではなくそれを読む。
- 税の実機Evidenceを、MFの税区分名ではなく JDL 側の literal（課区・税区・税入力方法・税額規則）と科目で索引し、入力元ごとの Human マッピングと分ける。これで 0870〜0878 の JDL Evidence を弥生でも再取得なしに使える。

回帰の基準: FY2026-05・FY2027-05 の formal CSV がバイト単位で同一（SHA-256 `ec2bcc3b…`、`090f3633…`）であること、および既存テスト全件。
