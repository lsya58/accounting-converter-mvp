# 弥生（仕訳日記帳 汎用形式・インポート形式）→ 共通Journal

最終更新: 2026-11-01

実データ1件（顧問先1社、private、Git管理外）から確定した入力形式と、読み込み部分の仕様です。顧客の値（会社名・科目名・摘要・金額）はこの文書に書きません。

## 形式の判定

| 項目 | 実測 |
|---|---|
| 種類 | 弥生会計デスクトップの帳票「仕訳日記帳」を **汎用形式** で書き出したもの。**弥生インポート形式でも、識別フラグ（2000/2111/2110/2100/2101）付きの仕訳データでもない** |
| 文字コード・改行 | CP932（Shift_JIS では読めない文字を含む）、BOMなし、CRLF |
| 区切り・引用 | カンマ区切り、標準CSVの引用（摘要にカンマを含む行あり）。値の中の改行・ダブルクォートは0件 |
| 構成 | 前置き7行（帳票名・書式名・事業所名・処理日時・検索条件・集計期間・当日仕訳）→ `[表題行]`（31列）→ `[明細行]` / `[日次合計行]` / `[月度合計行]` |
| 日付 | 和暦 `令和YY年MM月DD日` |
| 規模 | 2,514仕訳、7,232明細行、2025-08-01〜2026-07-31（12か月、決算仕訳を含む） |
| 検算 | 日次合計285件・月次合計12件すべてが明細行の合計と一致。全仕訳で借方=貸方 |

既存の弥生読込（`observed_parser.py`、インポート形式25項目・識別フラグ前提）とは別形式のため、別の入力アダプタ `adapters/input/yayoi/journal_report_parser.py` を追加した。既存の読込を拡張する案は、行の種類・列・まとまり方の規則がすべて違い、既存テストの意味を変えるため不採用。共通モデル（仕訳・行の意味・内容ハッシュ・税情報）はそのまま使う。

## 仕訳のまとまり方

- **同じ日付・同じ伝票No.の連続した明細行 = 1仕訳**。伝票No.だけでは一意でない（9件が別の日付で再利用）
- 明細行は借方だけ・貸方だけ・両方のいずれか。空の側は税区分が「対象外」で、それ以外の列はすべて空
- 物理行はそのまま共通の行（行番号・行摘要）になる。仕訳単位に潰さない。同じ内容の仕訳も別々に保持する
- 形は100種類（上位: 1D1C 1,102、2D2C 518、2D1C 187、3D3C 132）

## 列ごとの扱い

| 分類 | 列 |
|---|---|
| A. 共通Journalに保持 | 日付、借方/貸方の勘定科目・補助科目・部門・金額、摘要（行ごと）、税区分（入力元の税の識別）、税額（明示）、税計算区分・請求書区分・仕入税額控除（税情報の属性） |
| B. JDLへ出せるがマッピングが必要 | 勘定科目・補助（対象会社のJDL科目一覧への Human 対応）、税区分＋請求書区分＋仕入税額控除（JDL 税の意味への Human 対応）、部門（今回のデータでは全行空） |
| C. JDLに保持先がない | 付箋1/付箋2（2行）、決算（本決・中決、7仕訳。JDLでの表し方は未確認）、生成元・期日・番号・仕訳メモ（今回は全行空。入っていれば検出する） |
| D. 意味が未確認 | 仕入税額控除「控除不可」の税額、特定できていない税区分1種類、調整・タイプの観測値以外の値（観測値以外は止める） |
| E. 出力に不要（根拠あり） | `[表題行]`の印、作業日付（入力日の記録）、仕訳番号（行のID）、伝票No.（まとまりの判定に使用。JDLの伝番は取込時に振り直される）、日次・月次合計行（検算後に破棄） |

## 税と金額

- 税計算区分はすべて「内税」。金額は税込で、税額は別列に明示されている
- **端数は四捨五入**: 切捨てと四捨五入で結果が分かれる行は、すべて四捨五入側と一致した
- **経過措置（仕入税額控除80%）の税額は、控除割合を掛けた後の値**（金額×10/110×0.8）。汎用形式では控除割合の適用前後が形式によって異なる、という公式の注意と整合する
- 請求書区分・仕入税額控除は、行の列だが税額のある側だけに属する。どちらか一方に決まらない行は止める
- 入力元の税の識別は「税区分｜請求書区分｜仕入税額控除」とした。経過措置の仕入が、通常の課税仕入のマッピングに乗らないようにするため
- 明示税額は JDL へそのまま引き継ぐ（MF は税額を持たないので従来どおり切捨て計算）。通してよい条件は下の「端数処理と明示税額」を参照

## 安全のための停止条件

見出し・前置きの不一致、帳票名が仕訳日記帳でない、書式名が汎用形式でない、検索条件付き（絞り込まれた帳票）、列数、和暦以外の日付、集計期間外、金額の書式、空の側に値がある、税区分のない税額、どちらの側か決まらないインボイス属性、同じ日付・伝票No.の非連続、借方≠貸方、日次・月次合計の不一致、観測していない調整・タイプの値、CP932で読めない。正式な読み込みは1件でも該当すれば失敗し、診断（`diagnose`）は問題のある仕訳を除いて件数と理由を返す。

## 明示税額の監査

- 出力する金額は弥生の税込金額、税額は弥生の明示税額。内税の行では「金額に税額を含む」関係がそのまま保たれる
- 明示税額は自動で再計算・補正しない。通す条件と止める理由は下の「端数処理と明示税額」
- 経過措置80%の税額は控除割合後の値なので、通常の課税仕入の書き方へ流すと税額の意味が変わる。税の識別を別にしたうえで、候補を出さない（Human の判断と JDL での表し方の確認が先）
- 売上の JDL 書き方（実機で確認済みの会社では 売　上/10%/外税・税込金額＋明示税額）が、この顧問先の JDL 会社でも同じかは Human 確認事項

## JDL科目一覧PDFの読込（2社で見つかった不足）

- **補助科目の一覧がページをまたぐ**: 親科目の行はページの先頭で繰り返されない。前ページが補助の途中で終わり、次ページの最初のデータ行が補助で、コードが増えていて、親科目と借貸が一致するときだけ親を引き継ぐ。それ以外は従来どおり止める
- **同じ名前が複数のコードにある**（流動・固定の区分などで実在する）: このアプリは科目を名前で選ぶため区別できない。該当する名前は選択肢から除外し、衝突として記録する（推測でコードを決めない）。同じ親の中の同名補助も同様。コードの衝突は従来どおり読み込みを止める
- **JDL側の補助名が取込欄（全角10字＝20バイト）を超える**: 既存の扱いどおり、会社設定の確定を保留する（会社Aで9件）。JDLで短くするか、使わないかは Human

## 端数処理と明示税額（2社）

JDL の端数処理（売上・仕入それぞれ）を会社設定に持つ（`JdlTargetContext.sales_tax_rounding` / `purchase_tax_rounding`）。税の意味の対応には影響しないので Tax Context の識別には含めない。未設定なら保存ファイルにも書かない（既存の会社設定のハッシュは変わらない）。

0877 の実機では、切捨てと四捨五入で分かれる売上の明示税額（切捨て値）がそのまま再Exportされた。ただしその会社の JDL 端数設定が記録されていないため、「JDL は明示税額を保持する」のか「会社設定で再計算した結果がたまたま同じ」なのかは区別できない。そこで、どちらの読み方でも結果が変わらない場合だけ通す。

| 明示税額 | 対象会社の端数 | 判定 |
|---|---|---|
| 端数が出ない（全方式で同じ値） | 問わない | 通す |
| 切捨て値 | 切捨て | 通す |
| 任意 | 未設定 | `HUMAN:JDL_TAX_ROUNDING_SETTING` |
| 切捨て値 | 四捨五入・切上げで値が変わる | `EXPLICIT_TAX_KEEP_UNVERIFIED`（再計算されると値が変わる） |
| 会社の端数の値（切捨て値ではない） | 四捨五入・切上げ | `EXPLICIT_TAX_COMPANY_ROUNDING_UNVERIFIED`（切捨て以外の値は未確認） |
| どの方式とも違う（経過措置80% など） | 問わない | `EXPLICIT_TAX_AMOUNT_UNVERIFIED` |

会社B（両方切捨て）: 弥生の明示税額はすべて切捨てと一致し、新しい Evidence は不要。会社A（売上切上げ・仕入四捨五入）: 弥生は四捨五入。仕入は会社の値と一致するが切捨て値でない426仕訳、売上は切捨て値だが切上げと違う76仕訳が止まる。**どちらも「JDL は明示税額を保持するか」が分かれば解消する**。

## 実機Evidenceの最小計画（2社）

推測した科目・税マッピングでは probe を作らない。バックアップを取った検証用会社でだけ行う。

0. **Human 確認（実機操作なし）**: MF 実データの JDL 会社（0877 の会社）の端数処理設定を確認する。切捨て以外なら、0877 は「JDL は明示税額を保持する」ことの証拠になり、会社Aの502仕訳分の端数 Evidence が不要になる
1. 0 で切捨てだった場合のみ: 会社Aの設定（売上切上げ）を写した検証用会社で、切捨て値と切上げ値が分かれる売上1件と、四捨五入値が切捨て値と違う仕入1件を Import・再Export する。保持なら両方そのまま、再計算なら会社の値に変わる。1回で「保持か再計算か」が確定する
2. 会社Aの残り（Human 確認後）: 上位の未検証の形（上位10で381仕訳）、軽減8%・経過措置80%・控除不可（75仕訳。先に JDL 画面で1件ずつ入力して書き方を確認）、決算仕訳（7仕訳。Human に入力方法を確認してから）

会社Bは、全対象外の2D2C 1仕訳だけ実機検証が必要（下の「再監査」）。最初の弥生→JDL の実機往復は会社Bで行う。

## 会社B 初回往復の再監査（2026-11-01）

**訂正**: 「会社Bは新しい Evidence が不要」は誤り。1仕訳が実機検証を要する。

- **2D2C**: 既存の2D2C Evidence（P01）は「借方の課税仕入10%が1行だけ」の形。会社Bの2D2Cは4行とも対象外で、この組み合わせは未検証（`SHAPE_TAX_COMBINATION_UNVERIFIED`）。
  - 前回の見落としの理由: 科目が未対応の間は照合が組み合わせ判定まで進まず、この不足が表に出なかった。
  - 修正: 形×税の判定（`shape_tax_combination_gaps`）を科目の対応と独立に行う。
    - 税区分が確認済みなら現在のブロッカーとして数える。
    - 候補だけなら「確認後に出るもの」として別に数える。
  - 判定内容は MF の組み合わせ判定と同じ関数を使っており、変更していない。
- **売上10%**: 確認済みの JDL 科目は 6121・9251 だけ。会社Bでは名前の一致しない科目に売上の行が1つある。6121 か 9251 に対応付ければ追加の検証は不要（金額に端数なし）。それ以外なら実機検証が必要。
- **照合の誤分類**: 照合結果の科目コードの不一致（最も近い既存 Evidence との比較）が、科目確認済みでも `HUMAN:ACCOUNT_MAPPING` と表示されていた。科目の問題は各行の対応結果からだけ数えるよう修正。

- **情報の完全保持を宣言できる条件**: JDLに入らない値が1件もないこと（監査記録が不要なこと）。
  - 会社Bは部門・生成元・付箋1があるため宣言しない。
  - 補助科目を「親科目だけ」で出す扱いも情報が落ちるため、現在は選べない（JDLへの補助登録を案内する）。

### 監査記録の安全性

- **書く順番**: 正式CSVの前に監査記録を `.pending` で書く。CSVができたら、CSVの SHA-256 を入れて確定し、`.pending` を消す。
- **確定直後の照合**（`verify_non_retained_audit`）
  - 原本の SHA-256
  - CSVの SHA-256
  - 仕訳ごとの一対一の対応
  - 値の件数と中身
- **失敗したとき**: CSV と監査記録をどちらも消し、失敗とする。正式CSVだけが残ることはない。
  - 途中で止まった場合は `.pending` が残り、照合は FAIL になる。
- **再実行**: 既存のCSV・監査記録・`.pending` がある保存先は使わない（上書きしない）。
- **保管先**: CLI の出力先は `data/private` だけ（顧客データのため）。
- **判定を分ける**: 往復照合は2つを別々に出す。
  - `verdict_jdl_roundtrip`: JDLに入ったもの
  - `verdict_information_outside_jdl`: JDLに入らないものの保全

### 検証用CSV（2D2C）

- 対象: 人の確認がすべて済み、形×税だけが未検証の仕訳。
- 本物のまま使うもの: 仕訳の形・日付・確認済みのJDL科目。
- 架空にするもの: 金額・摘要。
- 条件: 税のない行だけで、各行に借方・貸方が1つずつあること。それ以外は作らない。監査記録の対象になる情報を持つ仕訳も除く。
- 判定: 既存の厳密比較で PASS（1仕訳・2行）したときだけ、「2D2C・税の行なし」を Evidence として登録する。他の組み合わせには広げない。

### 準備したもの

- 事務所確認シート（private、35行）と、記入した行だけを保存する反映コマンド（`tools/yayoi_office_sheet.py`）。候補は OK と書かれない限り確定しない。
- 実機検証用ファイルの出力（`yayoi_formal_output.py --probe`）。
  - ファイル名に NOT_FOR_PRODUCTION が必須。
  - 対象は、人の確認がすべて済み、形×税の検証だけが残る仕訳に限る。
- 往復照合（`tools/yayoi_roundtrip_check.py`）。弥生 ↔ 正式CSV ↔ 再Export を次の観点ごとに数える。
  - 件数・行
  - 科目・補助・金額・税額・日付
  - 摘要・形・合計
  - 監査記録
  - 既存の厳密比較

## 会社Aの長い補助名（再調査）

- 事実
  - JDL 科目一覧の補助9件の名前が、取込CSVの補助名称欄（全角10字＝CP932 20バイト）を超える。
  - 親科目2つはそれぞれ補助が125件・160件あり、超えるのはそのうち4件・5件。
  - 会社Aの弥生の補助に、同じ名前・先頭10文字が同じものはない。
- 公式マニュアルの記述では、補助は「補助コードまたは補助名称のどちらか1つ」で取り込める。ただし、名称なし（コードだけ）の取込は実機で確認していない。現在の出力は常にコードと名称の両方を書く。
- 結論
  - 会社全体の確定を保留するのは必要以上に広い。この9件を選択肢から外せば、他の補助と全仕訳には影響しない。
  - ただし外すと、科目一覧の識別ハッシュと会社設定のハッシュがずれ、科目一覧の更新判定がいつも「変更あり」になる。除外した補助を記録する小さな設計変更が必要なため、今回は既存の保留を維持した。
  - JDL 側の名前は変えない。この9件を使う仕訳が出た場合だけ、「コードだけの補助」の実機確認を1件行う。

## 旧計画（会社1社時点、参考）


推測した科目・税マッピングでは probe を作らない。対象会社の科目一覧・税設定・Human の税区分確認がそろってから、次の2回に分ける。

1. **JDL 画面での自己Export（書き方を知るため）**：軽減8%仕入、輸出売上、経過措置80%、控除不可を JDL 画面で1件ずつ入力して書き出す。JDL が受け付ける課区・税区の書き方が分からないまま Import すると、1件の誤りでファイル全体の取込が失敗し、他のケースの判定まで止まるため、先に書き方を確かめる
2. **1回の Import・再Export バッチ（ケースごとに判定）**: 四捨五入の明示税額（仕入・売上）、逆側の課税仕入・課税売上（返品など）、上位の未検証の形（3D3C・4D4C・3D1C・5D5C など上位10で381仕訳）、手順1で書き方が分かった税区分。決算仕訳は、JDL での入力方法を Human に確認してから加えるか決める

形の94種類を94回確認しない。上位から加え、残りは「形によらず JDL のまとまり方が保たれるか」を判断できるだけの Evidence がそろった時点で、別途ルールとして検討する（Evidence なしには一般化しない）。
