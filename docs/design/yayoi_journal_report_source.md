# 弥生「仕訳日記帳」汎用形式 → 共通Journal

最終更新: 2026-11-01

実データ1件（顧問先1社、private、Git管理外）から確定した入力形式と、読み込み部分の仕様です。顧客の値（会社名・科目名・摘要・金額）はこの文書に書きません。

## 形式の判定

| 項目 | 実測 |
|---|---|
| 種類 | 弥生会計デスクトップの帳票「仕訳日記帳」を **汎用形式** で書き出したもの。**弥生インポート形式でも、識別フラグ（2000/2111/2110/2100/2101）付きの仕訳データでもない** |
| 文字コード・改行 | CP932（Shift_JIS では読めない文字を含む）、BOMなし、CRLF |
| 区切り・引用 | カンマ区切り、標準CSVの引用（摘要にカンマを含む行あり）。値の中の改行・ダブルクォートは0件 |
| 構成 | 前置き7行（帳票名・書式名・事業所名・処理日時・検索条件・集計期間・当日仕訳）→ `[表題行]`（31列）→ `[明細行]` / `[日次合計行]` / `[月度合計行]` |
| 日付 | 和暦 `令和YY年MM月DD日` |
| 規模 | 2,514仕訳、7,232明細行、2025-08-01〜2026-07-31（12か月、決算仕訳を含む） |
| 検算 | 日次合計285件・月次合計12件すべてが明細行の合計と一致。全仕訳で借方=貸方 |

既存の弥生読込（`observed_parser.py`、インポート形式25項目・識別フラグ前提）とは別形式のため、別の入力アダプタ `adapters/input/yayoi/journal_report_parser.py` を追加した。既存の読込を拡張する案は、行の種類・列・まとまり方の規則がすべて違い、既存テストの意味を変えるため不採用。共通モデル（仕訳・行の意味・内容ハッシュ・税情報）はそのまま使う。

## 仕訳のまとまり方

- **同じ日付・同じ伝票No.の連続した明細行 = 1仕訳**。伝票No.だけでは一意でない（9件が別の日付で再利用）
- 明細行は借方だけ・貸方だけ・両方のいずれか。空の側は税区分が「対象外」で、それ以外の列はすべて空
- 物理行はそのまま共通の行（行番号・行摘要）になる。仕訳単位に潰さない。同じ内容の仕訳も別々に保持する
- 形は100種類（上位: 1D1C 1,102、2D2C 518、2D1C 187、3D3C 132）

## 列ごとの扱い

| 分類 | 列 |
|---|---|
| A. 共通Journalに保持 | 日付、借方/貸方の勘定科目・補助科目・部門・金額、摘要（行ごと）、税区分（入力元の税の識別）、税額（明示）、税計算区分・請求書区分・仕入税額控除（税情報の属性） |
| B. JDLへ出せるがマッピングが必要 | 勘定科目・補助（対象会社のJDL科目一覧への Human 対応）、税区分＋請求書区分＋仕入税額控除（JDL 税の意味への Human 対応）、部門（今回のデータでは全行空） |
| C. JDLに保持先がない | 付箋1/付箋2（2行）、決算（本決・中決、7仕訳。JDLでの表し方は未確認）、生成元・期日・番号・仕訳メモ（今回は全行空。入っていれば検出する） |
| D. 意味が未確認 | 仕入税額控除「控除不可」の税額、特定できていない税区分1種類、調整・タイプの観測値以外の値（観測値以外は止める） |
| E. 出力に不要（根拠あり） | `[表題行]`の印、作業日付（入力日の記録）、仕訳番号（行のID）、伝票No.（まとまりの判定に使用。JDLの伝番は取込時に振り直される）、日次・月次合計行（検算後に破棄） |

## 税と金額

- 税計算区分はすべて「内税」。金額は税込で、税額は別列に明示されている
- **端数は四捨五入**: 切捨てと四捨五入で結果が分かれる行は、すべて四捨五入側と一致した
- **経過措置（仕入税額控除80%）の税額は、控除割合を掛けた後の値**（金額×10/110×0.8）。汎用形式では控除割合の適用前後が形式によって異なる、という公式の注意と整合する
- 請求書区分・仕入税額控除は、行の列だが税額のある側だけに属する。どちらか一方に決まらない行は止める
- 入力元の税の識別は「税区分｜請求書区分｜仕入税額控除」とした。経過措置の仕入が、通常の課税仕入のマッピングに乗らないようにするため
- 明示税額は JDL へそのまま引き継ぐ（MF は税額を持たないので従来どおり切捨て計算）。実機で確認済みなのは切捨てと一致する明示税額だけなので、それ以外（四捨五入で分かれる値、控除割合後の値）は `EXPLICIT_TAX_AMOUNT_UNVERIFIED` で止める

## 安全のための停止条件

見出し・前置きの不一致、帳票名が仕訳日記帳でない、書式名が汎用形式でない、検索条件付き（絞り込まれた帳票）、列数、和暦以外の日付、集計期間外、金額の書式、空の側に値がある、税区分のない税額、どちらの側か決まらないインボイス属性、同じ日付・伝票No.の非連続、借方≠貸方、日次・月次合計の不一致、観測していない調整・タイプの値、CP932で読めない。正式な読み込みは1件でも該当すれば失敗し、診断（`diagnose`）は問題のある仕訳を除いて件数と理由を返す。

## 変換ワークフロー（2026-11-01 第2フェーズ）

`application/yayoi_jdl_workflow.py` が MF→JDL と同じ部品で正式出力までつなぐ。

| 段階 | 実装 | 再利用 |
|---|---|---|
| 入力形式 | `yayoi_journal_report_generic_identity()`、`YayoiJournalReportInputAdapter`、構造チェック | — |
| 会社設定 | 入力元＝弥生仕訳日記帳の profile を `create_yayoi_profile` で作る（税区分はすべて UNRESOLVED で保存）。CompanySetting は既存の保存部品をそのまま使う | CompanySettingStore（入力元を問わない） |
| 科目・補助・摘要の確認画面 | 確認サービスが会社設定の入力元で読み込み部分を切り替える | `CompanyMappingUpdateService`（MF と同じ画面・保存） |
| 摘要の置換 | 行ごとの摘要も置換の対象にした（MF は結果が変わらない） | MF の置換辞書・候補・一括確認 |
| 税区分の確認 | `application/yayoi_review.py`：識別子ごとに件数・候補・マッピング状態・Evidence 状態。`confirm_tax_identity` で1件ずつ保存 | `MappingConfirmationService` |
| Evidence・preflight・出力 | 仕訳ごとに止まり理由を持ち主付きで返す `assess`、全部 0 なら既存の変換サービスへ | 組み合わせ判定、JDL 税の意味、出力処理、期別出力 |
| JDLに保持先がない情報 | 付箋などは HUMAN、決算仕訳は SYSTEM_EVIDENCE で止める（摘要へ連結も削除もしない） | — |

対象 JDL 会社の科目一覧と税設定がない間は、CompanySetting を作れない（既存の設計どおり、会社設定は JDL の科目一覧を土台にする）。その間にできるのは、入力元の確認項目の集計（`tools/yayoi_review_sheet.py`、名前入りの一覧を data/private にだけ書く）と、JDL会社に依存しない判断（摘要の置換）を弥生用 profile に保存すること。

Windows 画面（Qt）は変更していない。この環境では Qt を動かせないため、画面からの操作は未確認。

## 明示税額の監査

- 出力する金額は弥生の税込金額、税額は弥生の明示税額。内税の行では「金額に税額を含む」関係がそのまま保たれる
- 切捨てと一致しない税額は自動で再計算・補正しない。実機で確認するまで `EXPLICIT_TAX_AMOUNT_UNVERIFIED` で止める
- 経過措置80%の税額は控除割合後の値なので、通常の課税仕入の書き方へ流すと税額の意味が変わる。税の識別を別にしたうえで、候補を出さない（Human の判断と JDL での表し方の確認が先）
- 売上の JDL 書き方（実機で確認済みの会社では 売　上/10%/外税・税込金額＋明示税額）が、この顧問先の JDL 会社でも同じかは Human 確認事項

## 弥生インポート形式を追加で取る価値

同じ事業所・同じ期間の「弥生インポート形式」があれば、次を突き合わせられる。待たずに進められるが、取れれば確実性が上がる。

| 比較項目 | 解消できること |
|---|---|
| 経過措置80%の行の税額 | 控除割合の適用前の値が取れる。JDL にどちらを入れるべきかの判断材料 |
| 識別フラグ（2110/2100/2101）と、今回の「同日・同伝票No.の連続行」 | まとまり方の規則を独立に検証できる |
| 決算区分の表し方 | 決算仕訳の扱いの判断材料 |
| 税区分・請求書区分の表記 | 汎用形式との対応表 |

## 実機Evidenceの最小計画（対象 JDL 会社の設定がそろってから）

推測した科目・税マッピングでは probe を作らない。対象会社の科目一覧・税設定・Human の税区分確認がそろってから、次の2回に分ける。

1. **JDL 画面での自己Export（書き方を知るため）**：軽減8%仕入、輸出売上、経過措置80%、控除不可を JDL 画面で1件ずつ入力して書き出す。JDL が受け付ける課区・税区の書き方が分からないまま Import すると、1件の誤りでファイル全体の取込が失敗し、他のケースの判定まで止まるため、先に書き方を確かめる
2. **1回の Import・再Export バッチ（ケースごとに判定）**: 四捨五入の明示税額（仕入・売上）、逆側の課税仕入・課税売上（返品など）、上位の未検証の形（3D3C・4D4C・3D1C・5D5C など上位10で381仕訳）、手順1で書き方が分かった税区分。決算仕訳は、JDL での入力方法を Human に確認してから加えるか決める

形の94種類を94回確認しない。上位から加え、残りは「形によらず JDL のまとまり方が保たれるか」を判断できるだけの Evidence がそろった時点で、別途ルールとして検討する（Evidence なしには一般化しない）。
