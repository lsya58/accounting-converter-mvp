# 1. 文書の目的

本書は、異なる会計ソフト間で仕訳データを移行する際に発生する、CSV形式・項目体系・会計データ表現の違いによる作業負荷および取込エラーを解消する「会計ソフト間仕訳データ変換システム」の要求を定義する。

本システム全体の目的は、

> **異なる会計ソフト間の仕訳データを、安全かつ容易に変換できる環境を提供すること**

である。

本システムの価値は単なるCSV形式変換ではない。他社会計ソフトに存在する日々の全仕訳を、税理士事務所が普段使用している会計ソフトへ安全に取り込み、いつもの会計ソフト上で仕訳・元帳・補助元帳等を確認できるようにすることである。

製品ビジョンは、

> **会計ソフト間の仕訳データ変換・取込支援システム**

である。

初期MVPでは、

> **弥生会計から出力された仕訳データを、JDLへ取り込み可能な仕訳データへ変換すること**

を対象とする。

将来的には、マネーフォワード クラウド会計、freee等を入力元として追加する。

# 2. 背景

## 2.1 実務上の状況

税理士事務所と顧問先企業では、異なる会計ソフトが使用される場合がある。

例：

* 税理士事務所：JDL
* 顧問先A：弥生会計
* 顧問先B：マネーフォワード クラウド会計
* 顧問先C：その他会計ソフト

この場合、顧問先側で作成された仕訳データを税理士事務所側のJDLへ移行する必要がある。

各会計ソフトにCSV等の入出力機能があっても、

* 項目数
* 項目順
* 勘定科目
* 補助科目
* 税区分
* 部門
* 日付形式
* 複合仕訳表現
* 文字コード
* 必須項目
* 識別情報

等が異なるため、正常に取り込めないことがある。

## 2.2 MVP方向を変更した根拠

初期検討ではJDLから弥生会計への変換を想定していた。

その後、実務利用者へのヒアリングにより、

> **税理士事務所ではJDLを使用し、顧問先等では弥生会計やマネーフォワード等が使用されており、他社会計ソフトからJDLへ仕訳を取り込む業務で実際に問題が発生している**

ことを確認した。

特に、CSVによる取り込み機能は存在するものの、弥生会計等からJDLへの取り込みが正常に成功していないことが確認された。

このため、MVPでは実務上の優先度が高い、

**弥生会計 → JDL**

を優先する。

従来検討していた、

**JDL → 弥生会計**

は将来拡張候補として保持する。

## 2.3 追加ヒアリングで判明した実業務

税理士事務所ではJDLを使用している。一方、一部顧問先では弥生会計など別の会計ソフトを使用している。

弥生側には日々の全仕訳が存在するが、弥生から出力した仕訳データをJDLへそのまま取り込めないため、現在は月末・月次の残高等だけをJDLへ手入力しているケースがある。

その結果、以下の問題が発生している。

* 月次結果はJDLで確認できる
* 個々の仕訳や詳細を確認するには弥生を開かなければならない
* 税理士事務所側はJDLの操作に慣れているため、可能なら全仕訳をJDLで確認したい
* CSV取込のための手作業修正や原因調査に時間がかかる

現在の具体的MVPでは、

```text
弥生会計
↓
変換
↓
JDL IBEX出納帳で取り込める仕訳ファイル
↓
JDL上で全仕訳を利用可能
```

を目標とする。

# 3. 解決すべき課題

## P-01 CSV仕様差異

入力元会計ソフトとJDLでCSV仕様が異なり、そのまま取り込めない。

## P-02 会計項目差異

勘定科目、補助科目、税区分、部門等の表現・コード体系が異なる。

## P-03 JDL取込エラー原因の特定困難

どの仕訳・項目に問題があるか利用者が把握しにくい。

## P-04 CSV手修正負担

Excel等による手作業加工が発生する。

## P-05 誤変換リスク

金額、貸借、科目、税区分、仕訳構造等の誤変換が会計・税務処理へ影響する。

## P-06 顧問先ごとに会計ソフトが異なる

ソフトごとに異なる変換方法を理解する必要がある。

## P-07 JDL側問題との切り分け困難

CSVデータ側の問題か、JDL側の設定・仕様・不具合等か判断しにくい。

実務確認により、JDLから出力されたCSVであっても別環境のJDL IBEX出納帳へそのまま取込できないケースが確認された。JDLファイル形式の互換性と、取込先JDL内の勘定科目・補助科目・部門・税区分等のマスター互換性は別問題として扱う。

## P-08 現行作業工数が不明

CSV修正・再取込等に必要な作業時間が定量化されていない。

## P-09 実仕様確定前の誤実装リスク

公式ドキュメント、画像、ログ、実データ観測結果を混同して正式仕様として扱うと、誤った変換ロジックを固定してしまう危険がある。

本システムでは以下を明確に分離する。

* 公式ドキュメント上の仕様
* 実データから観測された仕様
* 実データ検証済みの正式FormatProfile
* 診断用途のObserved Behavior

## P-10 全仕訳参照環境の分断

JDLへ月末・月次残高のみを手入力している場合、JDL上では個別仕訳や補助元帳レベルの詳細確認ができず、詳細確認のたびに弥生等の入力元ソフトを開く必要がある。

## P-11 毎月反復するMapping作業

同じ顧問先について毎月繰り返し変換する場合、勘定科目・補助科目・部門・税区分等の対応関係を毎回手入力すると作業負荷が大きい。安全に確定した対応関係はローカルのConversion Profileとして再利用できる必要がある。

## P-12 拡張子依存による形式誤判定

仕訳エクスポートが `.csv` ではなく `.txt` 等で提供される可能性がある。拡張子だけで形式を断定すると誤判定につながるため、FormatProfileに基づいて対応する仕訳データファイルを判定する必要がある。

# 4. システムの目的

> **入力元会計ソフト固有のファイル仕様を利用者が詳細に理解しなくても、日々の全仕訳をJDLへ取り込める形式へ安全に変換し、税理士事務所が普段使用するJDL上で仕訳・元帳・補助元帳等を確認できる状態を実現する。**

MVPでは弥生会計からJDLへの変換を対象とする。

---

# 5. 基本方針

## BP-01 正確性優先

速度よりも会計データの正確性・完全性を優先する。

## BP-02 Silent Failure禁止

変換不能データを利用者へ知らせず削除・補正・別仕訳化してはならない。

## BP-03 元データ保護

入力元ファイルを変更・上書きしない。

## BP-04 問題箇所明示

対象仕訳・項目・値・原因を確認可能にする。

## BP-05 MVP優先

初期MVPは弥生会計→JDLに限定する。

## BP-06 将来拡張

製品全体を弥生→JDL専用ソフトとして固定しない。Input Adapter、Common Journal Model、Mapping / Validation、Output Adapterのvendor-neutralな構造を維持する。

将来候補は、Money Forward→JDL、freee→JDL、その他会計ソフト→JDL、市場検証後に必要な他出力先ソフトである。ただし将来機能をMVP要件として実装必須にしない。

## BP-07 ローカル処理

MVPでは会計データ処理を利用者管理下のPC内で完結し、会計データを外部サービスへ送信しない。

## BP-08 仕様確定の段階管理

弥生・JDLいずれも、実データ取得前に正式Adapterや正式FormatProfileとして有効化しない。

弥生については、弥生株式会社公式サポートの「弥生取り込み（インポート）形式（弥生会計05以降）」を `OFFICIAL_DOCUMENTED` / `REAL_DATA_VERIFICATION_PENDING` として保持するが、使用中製品・バージョン・実出力CSV確認後にのみ正式FormatProfileへ昇格できる。

JDLについては、JDL IBEX出納帳 35.5 の実データからObserved Behaviorを確認しているが、正式JDL仕様としては扱わない。

## BP-09 不完全出力防止

Error、Fatal、未解決Mapping、Output Validation失敗、予期しない例外がある場合、正式出力を生成しない。正常な一部仕訳だけを部分出力してはならない。

正式出力は一時ファイルへ生成・検証した後、成功時のみatomic replaceする。既存出力ファイルは利用者の明示的な上書き許可なしに置換しない。

## BP-10 Conversion Profileのローカル保存

同じ顧問先や同じ変換条件を翌月以降再利用できるよう、安全に確定した対応関係をConversion Profileとしてローカル保存可能にする。

Profileには入力形式、出力形式、勘定科目Mapping、補助科目Mapping、部門Mapping、税区分Mapping、その他安全に確定した変換設定を保存できる。

Profileへ仕訳本文、金額データ、摘要本文、実会計ファイルそのものを保存しない。クラウド同期・外部送信は行わない。

## BP-11 自動変換と推測修正の分離

保存済みProfileや明示的に確認済みの変換Ruleは自動適用できる。ただし未知の科目、補助科目、税区分、部門、日付形式、列構造、複合仕訳表現等を名前の類似だけで自動確定しない。

未解決Mappingが存在する場合は、変換を停止し、ユーザー確認とMapping確定後に再実行する。

# 7. 想定利用シーン

## UC-01 弥生→JDL変換

1. 弥生会計から仕訳データファイルを出力
2. システムへ仕訳データファイルを入力
3. 弥生形式判定
4. 仕訳解析
5. JDL向け変換
6. エラー・未確定項目確認
7. 必要なマッピング指定
8. 再検証
9. JDL取込用ファイル生成
10. 検証結果レポート保存
11. JDLへインポート

## UC-02 JDL取込失敗時

JDLでエラーが発生した場合、保存した検証レポートを確認し、本システムが検証可能なデータ側の問題の有無を確認する。

本システムは「JDL側が原因」と断定せず、

> **本システムが検証可能なデータ項目では問題が検出されていない**

ことまでを示す。

### 現在実装済みの切り分け支援

JDL CSV Diagnostic Analyzerにより、JDLへ取り込めないCSVについて、CSV構造、文字コード、行分類、JDL診断コメント、マスター不一致候補、Observed Schema Fingerprint、Observed Journal Group Candidateを診断できる。

これは変換コア・正式JDL Output Adapterとは独立した診断機能であり、JDL側障害を断定しない。

## UC-03 初回変換とConversion Profile保存

1. 弥生仕訳ファイルを選択
2. ファイル構造を解析
3. JDLとの差異を検出
4. 勘定科目・補助科目・部門・税区分等のMappingをユーザーが確認
5. 安全に確定した対応関係をConversion Profileとしてローカル保存
6. 変換
7. 検証
8. JDL取込ファイル生成

## UC-04 翌月以降の保存済みProfile利用

1. 弥生仕訳ファイルを選択
2. 保存済みConversion Profileを選択
3. システムが自動検証
4. 問題がなければ1回の変換操作でJDL取込ファイルを生成
5. Verification Reportを生成

## UC-05 未知Mapping出現時

1. 保存済みProfileを選択
2. 新しい勘定科目・補助科目・部門・税区分等の未知Mappingを検出
3. 自動変換を停止
4. ユーザーがMappingを追加・確認
5. Profileを更新
6. 再実行

# 12. 現在のテスト方針

実顧客データはGit管理対象にしない。

Git管理されるCSVは `tests/fixtures/` 配下の完全架空データのみ許可する。

GitHub Actionsでは、push / pull_request時に以下を実行する。

```bash
env PYTHONPATH=src python3 -m unittest discover -s tests -v
```

また、`tests/fixtures/` 配下以外のCSVがGit管理対象に含まれていないことを検査する。

# 13. 複合仕訳

複合仕訳をMVPで正式対応するかは実データ確認後に決定する。

非対応とした場合でも、複合仕訳らしき構造を単純仕訳として正常変換してはならない。

検出した場合はErrorとする。

# 15. 操作性

## US-01

仕訳データファイル内部構造を利用者が直接編集しなくてよいこと。

## US-02

基本操作を、

**ファイル指定 → 内容確認 → 必要な対応 → 変換 → 検証 → 出力**

で行えること。

## US-03

人間が理解できるエラー説明を表示すること。

## US-04

初回や未知Mapping出現時は人間の確認を要求し、一度安全に設定した対応関係は翌月以降再利用できること。

## US-05

通常月は、保存済みProfileを選択したうえで、問題がなければ可能な限り少ない操作で変換・出力できること。
