# 弥生「控除不可」の税区分確認と、将来の修正・承認フロー設計（2026-11-09）

顧客の値は書かない。税理士の回答は「調査方針・暫定的な見解」であり、特定のJDL税区分への変更の正式承認ではない。

## 1. 税理士回答から確定できること／できないこと
| 確定できる | まだ判断できない |
|---|---|
| 税理士は、控除不可が入力ミスの可能性を指摘している（見解） | 各仕訳が実際に誤入力か（取引実態の確認が未了） |
| 海外商品購入の1件は元の税区分が誤りとの見解 | その取引が国外取引（不課税）／輸入貨物への課税／その他のどれか |
| JDLに弥生の控除不可に直接対応する税区分はない（既存Evidence） | 「非課税仕入」をJDLの非課税区分へ対応づけてよいか（根拠未確認） |
| JDL上で誤りを発見・修正できる状態にしたい（要望） | 非仕入（税区空欄）が申告上の同等扱いか |

①②③と仕訳ID: 過去の質問文は記録に残っておらず、①②を425／565のどちらに紐づけるかは確認できない。③の「海外商品購入」は摘要の内容から3558と整合するが、番号の対応そのものは記録がないため、利用者が確認する。①②は同じ回答（理由不明）なので扱いは変わらない。

## 2. 国税庁の論点（取引実態ごと。AIは判定しない）
国税庁タックスアンサーNo.6209（輸出免税・国外取引の範囲）、No.6210（非課税となる取引）、No.6563（輸入取引の課税）。国外取引の不課税、法定の非課税、輸入貨物への課税は別概念。商品の所在地・輸入通関・輸入申告者・輸入消費税の有無は元データから判定できず、追加確認が必要。（本ドキュメント作成時、各ページの本文は取得して再確認していない。税理士が一次資料で確認すること。）

## 3. JDLで元の税区分を保持する方法
| 案 | 判定 |
|---|---|
| A 既存税区分で同等に保持 | 実機で確認済みの候補は非仕入（税区空欄）のみ。10%／8%の別・区分記載・控除不可は残らない。税務上の同等性は税理士確認待ち |
| B 税理士承認後に再分類 | 既存の `noncredit_approval`（会社限定・SIGNOFF記録必須、16行のみ）が該当。別区分への再分類は承認条件が未提示のため未実装 |
| C 元区分をJDLの欄へ補足保持 | **実機Evidenceなし → 不可と判定**。摘要追記は、既存摘要の改変・64バイト超切詰め（JDLは黙って切る）・取込後保持が未検証のため採用しない |
| D 外部の監査レポート | 既存の `.audit.json`（`noncredit_tax_lines`）。「JDL内に保持できた」とは表示しない |

## 4. 新しいJDL Probeの要否
現時点で必須のProbeはない。Cを実現するなら「摘要末尾に元区分を追記→64バイト内で取込→再Exportで保持」を1ファイルで確認する最小Probeだが、税理士がそもそも摘要追記を望むか（既存摘要の改変を許すか）を先に確認する。それまで作らない。

## 5. 将来の修正・承認フローのデータモデル（今回は未実装）
別々のレコードとし、元データを上書きしない。仕訳ID＋元の行番号で参照する。
1. SourceTaxFacts（変更不可）— 実装済み: `application/tax_review_facts.TaxReviewLine`
2. ReviewedTransaction（税理士が確認した取引実態・日付・確認者）
3. CorrectionCandidate（修正候補。元値・候補値・根拠）
4. ApprovedCorrection（承認済み修正指示。元値・変更後値・判断理由・承認者・日付・Evidence ID）— 既存の分割承認／控除不可SIGNOFFの会社別profile保存を再利用
5. ConversionResult（JDLへ出した値）と LossRecord（残らない情報）— 既存 `.audit.json`
6. Evidence・承認履歴
再変換は既存の再診断で行う。承認があっても他のBLOCK（構造Evidence不足など）が残れば READY にしない。

## 6. BLOCK依存関係の確認（2026-11-09、campaign 第27章）
税理士が「控除不可のままJDLでは非仕入（税区空欄）」と判断して承認を記録した場合、16行設定では 565・3558 は変換可能、425 は伝票分割の承認だけが残る（試算）。64行設定では技術Evidenceが範囲外のため不可。元の税区分を修正する判断の場合は、弥生で修正して出力し直し、再診断する（修正後の区分の対応確認は通常の税区分確認画面で行う）。アプリ内の修正指示（第5章の4）は未実装。画面の見通しは controller の試算で毎回計算し、承認や READY を作らない。

## 7. 税理士の追加回答: 海外購入（2026-11-09）
**運用方針として記録**（個別仕訳の承認記録ではない）: 「海外からの購入は全て非課税仕入でいいっていうこと？」に対し税理士は「いいよ」と回答。

### 7.1 3558への当てはめ（元データとの照合）
- 3558 の控除不可の明細は1明細（消耗品費、通販サイトでの購入、10%・区分記載・控除不可・内税・税額0）。元の値は変更しない。
- 会社Aの保存設定では、弥生「非課仕入」は確認済みで JDL **非仕入（課区34＝非課税仕入）**、弥生「対象外」「対外仕入」は JDL **対象外**（課区空欄）に対応する。税理士の「非課税仕入」は JDL の非仕入（34）を指すと読めるが、**意図の確認は残す**（下の7.3）。
- 3558 の行き先の候補（元値と修正候補を区別）:

| 経路 | 元の弥生データ | JDLへ出る値 | 記録 | 現状 |
|---|---|---|---|---|
| (a) 控除不可のまま別表現で取込 | 控除不可のまま | 非仕入・税区空欄 | 監査記録に「控除不可→非仕入」と失われる情報 | 仕訳単位の税理士承認（`noncredit_approval`、16行のみ）で可能。未承認 |
| (b) 元の税区分が誤りとして修正 | 弥生で「非課仕入」に修正し再出力 | 非仕入（既存の確認済み対応） | 修正は弥生側の履歴。アプリには元の控除不可は残らない | 既存の運用で可能（16行・64行とも既存Evidenceで通る試算あり） |
| (c) 国外取引として不課税 | 弥生で「対象外」等に修正 | 対象外 | 同上 | 既存の運用で可能。ただし税理士の発言は「非課税仕入」 |

(a) と (b) は JDL 上の出力が同じでも、判断の意味（元データを残すか、誤りとして直すか）と監査の記録が異なる。**同じ判断として扱わない。**

### 7.2 制度上の区別（AIは判定しない）
国外で引き渡される取引は不課税（国外取引）、法定の非課税取引は限定列挙、輸入貨物は税関で輸入消費税が課される（課税仕入れとして控除対象になり得る）。「海外購入＝非課税仕入」は税理士の運用上の扱いであり、制度上の分類とは一致しない場合がある。申告への影響の評価は税理士の判断。

### 7.3 アプリでの扱い
- 「海外購入」を判定する汎用ルール・自動変換は追加しない（取引先名・摘要からの推定もしない）。
- 方針があっても、対象の仕訳・明細を事務所が指定し、仕訳単位の承認（a）または弥生での修正（b）を経るまで BLOCK を維持する。構造Evidence・税額の未解決があれば、それも BLOCK のまま。
- 最小限の追加確認: (1) 3558 は (a)・(b)・(c) のどれか（JDLの区分は「非仕入（非課税仕入）」でよいか）。(2) 方針の対象範囲（どの仕訳が「海外購入」か。例: 3558 の同じ仕訳内に、海外事業者名で「適格・100%」の別明細がある。これに方針を当てはめるかは事務所が決める）。(3) (b) の場合、弥生側で修正して再出力するか。
- 税理士が区分と範囲を確定した場合の実装可否: (b) は追加実装なしで可能（再出力→再診断）。アプリ内で「元値を残したまま修正後の区分で出す」修正指示（第5章の4）を作る場合は、第8章の仕訳単位の承認（内容identityへの紐づけ・承認者・参照・日付・監査）を再利用でき、修正後の区分は既存の確認済み対応（非課仕入→非仕入）のEvidenceを使う。未実装。

## 8. 控除不可の承認は仕訳単位（JOURNALS_V1、2026-11-09）
- 監査結果（修正前）: 承認は `profile.tax_mappings[弥生の税区分identity]` に1件で、判定 `is_approved_line(line)` は identity しか見ていなかった。10%控除不可を承認すると、取引内容の異なる 565 相当と 3558 相当の両方、さらに将来の同じ identity の仕訳も変換対象になった（再現テストで確認）。軽減8%は別 identity で波及しない。仕訳単位の承認者は追跡できず、元仕訳が変わっても承認は失効しなかった。
- 修正後:
  - 承認は対象の仕訳を明示する（CLI `--source` と `--journal`、関数は `journals=` 必須）。mapping の metadata に `noncredit_scope=JOURNALS_V1` と仕訳ごとの記録（内容identity・元の明細・承認者・税理士・参照・日付）を保存。同じ identity の後続の承認は追記され、各仕訳の記録は個別に残る。
  - 各明細はパーサで所属仕訳の内容identity（`line_journal_content_sha256`）を持つ。内容identityはファイル名・行番号・伝票番号・仕訳番号を含まず、日付・借貸・科目・補助・金額・税・摘要が同じなら同一。
  - 判定: 明細の仕訳identityが承認記録にある場合だけ変換。加えて正式診断で、承認記録のない控除不可の仕訳には `HUMAN:TAX_MAPPING` を明示的に付ける（Evidence照合の結果に依存しない）。
  - 失効: 内容が変わった仕訳は identity が変わり BLOCK。未変更の仕訳を別ファイル名で再出力した場合は一致する。
  - 内容が同一の仕訳が複数ある場合は区別できないため、承認を拒否し、承認済みの内容でも重複していれば BLOCK。
  - 仕訳一覧のない従来形式の承認（identity単位）は無効（`NONCREDIT_APPROVAL_NOT_SCOPED_TO_JOURNALS`）。実AppDataに既存の承認は0件だった。
  - 16行の承認は64行に引き継がない（従来どおり）。承認時も64行では拒否。
  - 監査記録は仕訳ごとの承認（内容identity・ラベル・税理士・参照・日付）を出力。
  - 通常の確認済み税区分mappingは従来どおり会社設定として新しい仕訳にも再利用される（回帰テストあり）。
